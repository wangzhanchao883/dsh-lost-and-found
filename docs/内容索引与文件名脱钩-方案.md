> 版本：草案 v1（2026-09-14）｜状态：**待用户确认，尚未动代码**
> 目标读者：插件作者（用户）+ 实施者（DSH）
> 关联插件：`dsh-lost-and-found`（本地源码 `D:\workout\deepseekharness\dsh-plugin\dsh-lost-and-found`）

## 0. 触发案例（真实发生，必须回归验证）

用户在 `D:\AI视频学习\素材库\封面\` 找一张「空洞骑士骑鲸鱼」的图，按文件名怎么都搜不到——
因为文件名叫 **`卡通风格骑马.png`**，里面画的却是**骑鲸鱼**。

两次故障模式：
1. **按文件名搜不到**：名字里没有任何"鲸鱼/空洞骑士"线索（名字本身是错的）。
2. **按多关键词搜直接归零**：当前检索是"每个关键词都必须命中某一列"（AND 语义）。
   搜「空洞骑士 鲸鱼」时，"鲸鱼"在该文件的 `name/path/tags/summary/image_desc/excerpt` 里全都不存在 → 结果 0 条。

**用户的核心诉求**：人类只记得"内容"，文件名很可能是错的。索引要**记内容**，检索要**文件名和内容一起搜**，并且能看出**名字与内容不符**。

### 1.2 关键缺陷：内容字段一个都没写过

`files` 表**已经有** `summary` / `excerpt` / `image_desc` / `tags` 四个内容列，
`core/search.mjs` **已经在 LIKE 搜这四列**——但全库 `enrich` 状态统计：

```
none: 6584      ← 全部文件，没有任何一个被富化过
```

即：**内容检索的管道两端都通，中间没有泵。** 1231 张图片 `image_desc` 全为空。
所谓"待处理 258 个待读内容"是一个无人消费的计数。

### 1.3 图片元数据不可依赖（已实测）

对 1231 张图抽样探测 PNG 文本块 / XMP：

- 670 个 PNG 中，仅 **90 个**带文本/EXIF 块；其中含 prompt/AIGC 关键词的只有 **2 个**
- 那 2 个（豆包生成）的 XMP 内容只有 AIGC 合规标签：
  `{"Label":"1","ContentProducer":"doubao","ProduceID":"0ddbe6…","ReservedCode1":"","ReservedCode2":""}`
  —— **没有提示词**
- 同一张图的不同拷贝，元数据还会被转存工具剥掉
  （`素材库\封面\卡通风格骑马.png` 无元数据；`GPT浏览器下载\卡通风格骑马.png` 有）

**结论：图片内容语义只能靠视觉模型看图，没有白拿的捷径。**

### 1.4 现有检索打分（`core/search.mjs`）

```
LIKE_COLUMNS = [name, path, tags, summary, image_desc, excerpt]
WEIGHT       = { name:50, tags:30, path:20, summary:15, image_desc:10, excerpt:8 }
完全同名     +80
7 天内 / 30 天内  +6 / +3
```

SQL 层：每个关键词一组 `(col1 LIKE ? OR … OR col6 LIKE ?)`，多关键词之间 **AND**。
命中来源集合 `_hitIn` 已回传，但渲染出来是英文列名（`命中：name / path`）。

## 2. 设计目标 / 非目标

### 目标
1. **内容可搜**：正文/画面里出现过、文件名里没有的词，也能搜到。
2. **可解释**：结果标注「命中文件名 / 命中内容 / 两者」，仅内容命中时明确提示"文件名里没有这个词"。
3. **脱钩可见**：能列出"文件名与内容明显不符"的文件，并给**建议名**。
4. **零破坏**：插件只读用户文件的铁律不变；不改名、不移动、不写 ADS。

### 非目标（本期不做）
- 视频/音频内容理解（成本高、收益低）
- 压缩包内文件展开索引
- 全文检索服务化（FTS5 仍按可用性可选加速，不作依赖）

---

## 3. 数据模型（schema v3 → v4）

`files` 表新增列（全部可空，老库 `migrate()` 补列，索引是派生的可重建数据）：

```sql
ALTER TABLE files ADD COLUMN content_desc      TEXT;     -- 一句话内容描述（人可读）
ALTER TABLE files ADD COLUMN content_text      TEXT;     -- 正文摘录（截断，纯文本类）
ALTER TABLE files ADD COLUMN content_kind      TEXT;     -- document | image | none
ALTER TABLE files ADD COLUMN content_tags      TEXT;     -- 内容关键词（可与 tags 合并，建议独立）
ALTER TABLE files ADD COLUMN name_content_score REAL;    -- 文件名与内容的词重叠度 0~1
ALTER TABLE files ADD COLUMN mismatch          INTEGER DEFAULT 0;  -- 0 正常 / 1 疑似不符
ALTER TABLE files ADD COLUMN enrich_at_ms      INTEGER;  -- 上次富化时间
ALTER TABLE files ADD COLUMN enrich_ver        INTEGER DEFAULT 0;   -- 富化规则版本，升级后失效重跑
ALTER TABLE files ADD COLUMN enrich_err        TEXT;     -- 失败原因（便于排障）
```

- 保留 `summary` / `excerpt` / `image_desc` / `tags` **不动**，检索继续兼容（老数据不丢）。
- `enrich` 状态机取值统一为：
  `none → text_done | described | skip | failed`，配 `retry_count` 上限（如 3）。

**为什么单独开 `content_*` 而不是复用旧列**：旧列语义已被"深度策略"（full/summary/meta）绑定，
新列需要独立的版本号（`enrich_ver`）以便日后换描述模板/换模型时批量失效重跑，互不干扰。

## 4. 分层设计

### L0 · 检索层改动（最小改动，收益最大）

1. `LIKE_COLUMNS` 追加 `content_desc`、`content_text`、`content_tags`。
2. 权重（建议值，保留"文件名优先"的直觉，但让内容命中不再被淹没）：

   | 列 | 现权重 | 建议 |
   |---|---|---|
   | name | 50 | 50 |
   | content_tags / tags | 30 | 32 / 28 |
   | path | 20 | 20 |
   | summary | 15 | 15 |
   | content_desc | — | 24 |
   | image_desc | 10 | 12 |
   | content_text / excerpt | 8 | 10 / 8 |

3. 命中来源中文化 + 语义分组：`_hitIn` 映射为
   `命中：文件名 / 内容 / 标签 / 路径 / 时间`，并新增一个布尔 `_contentOnly`。
4. **仅内容命中时的提示**（直接对准本次案例）：
   > 提示：该文件**文件名里没有**「鲸鱼」，是靠**内容**命中的（内容：空洞骑士 骑 鲸鱼 …），
   > 建议核对是否需要改名。
5. 新增检索参数：
   - `searchIn`: `both`（默认）/ `name` / `content` —— 用户明确只想按名字找时可切
   - `mismatchOnly`: 只看名字与内容不符的文件
6. 保留"索引不够用时实时兜底扫描"的现有行为（注意：兜底扫描**不写库**，因此兜底结果永远只有名字；文档里要写明这个限制，避免误导）。

### L1 · 本地零成本抽取（覆盖约 4500 个文本类文件，0 次模型调用）

新增独立子进程 `core/enrich.mjs`（与扫描器分开，自己的 PID 锁，可与扫描并行不冲突）：

| 输入 | 处理 | 产出 |
|---|---|---|
| `.md .txt .json .csv .log .srt .yaml .ini` | 直接读，折叠空白 | `content_text`（前 N 千字）+ 关键词 |
| `.docx .xlsx .pptx .epub` | `unzip` 读 `word/document.xml` / `xl/sharedStrings.xml` / `ppt/slides/*.xml` / XHTML，剥标签 | `content_text` |
| `.pdf` | 文本层抽取（**依赖待定，见 §7**） | `content_text` 或 `content_kind=none` |
| `.html .htm` | 剥标签 | `content_text` |
| 图片 | 不在此层处理 | 交给 L2 |
| 其他二进制 | 标记 `enrich='skip'` | — |

工程要点：
- **只读**：`readFileSync` + `statSync`，绝不写用户目录、不建临时文件（解压走内存 `node:zlib`）。
- **配额与限流**：`enrichBatchPerRun`（默认 300）、`enrichMaxFileMB`（复用 `maxFileMB`）。
- **断点续跑**：靠 `enrich` 状态 + `enrich_ver` 选批，进程被杀不丢进度。
- **优先级公式**（分数越高越先做）：
  ```
  priority = 时间分(7d:40 / 30d:20 / 90d:8)
           + 类型分(文档·表格·PDF:25 / 文本·代码:15)
           + 目录分(在 读书|工作|笔记|资料 等语义目录:+10)
  ```
- **失败重试**：`retry_count < 3` 才重排；超过标记 `failed` 并写 `enrich_err`。

**产出效果**：以后"记得正文里那句话、忘了文件名"能直接搜到。

### L2 · 图片内容（唯一需要模型钱的部分）

**沿用现有"模型在环"流程**（`file_index_pending_images` → `read_image` → `file_index_set_image_desc`），补四点：

1. **优先级队列**（新增 `file_index_image_queue`，或给 `file_index_pending_images` 加排序）：
   ```
   priority = AI生成图特征分(size>1MB:+15, png/webp:+10, 目录含 封面|素材|头像|下载|GPT浏览器:+25)
            + 时间分(7d:30 / 30d:15)
            + 尚无任何内容信息:+10
            - 截屏类(名含 屏幕截图|Screenshot):-15
   ```
   —— 你这次的图会排在第一批，不必等 1231 张跑完。
2. **描述模板**（写进 `content_desc`）：`主体 + 动作 + 场景/风格 + 来源线索`
   > 例：`空洞骑士（游戏角色）骑在鲸鱼背上，水下光柱与漂浮粒子，暗色奇幻插画，豆包AI生成`
3. **可搜词**（写进 `content_tags`，含图上文字）：`空洞骑士 鲸鱼 骑士 骑乘 豆包 AI 插画 游戏同人`
4. **批量看图循环**：每轮取 N 张（建议 8），连续 `read_image` 后统一写回；`imageQuotaPerRun` 由"每次 20"改为**每日配额**（如 150），让全量 1231 张在约 8 天内自然收敛。

**成本口径**：1231 张 = 1231 次视觉调用。分两档执行：
- 高价值子集（>1MB 且在下载/素材/封面/头像目录）：约 **150–300 张**，一次冲刺做完
- 其余：按日配额慢慢补

### L3 · 「文件名 ↔ 内容不符」报告（用户最想要的那件事）

新增工具 `file_index_mismatch({ limit, minScore })`：

1. **打分**（纯本地，零成本）：
   ```
   nameTokens    = 文件名去扩展名后按 空格/_/-/驼峰/中文2-gram 切词
   contentTokens = content_text + content_desc + content_tags 切词
   name_content_score = |nameTokens ∩ contentTokens| / max(1, |nameTokens|)
   mismatch = (content_desc 或 content_text 非空) AND name_content_score < 0.2 AND |nameTokens| >= 2
   ```
2. **建议名生成**（只展示，不执行）：取 `content_desc/content_tags` 中权重最高的 2–3 个实体词 + 原扩展名
   > `卡通风格骑马.png` → 建议 `空洞骑士-鲸鱼-豆包AI插画.png`
3. **铁律边界**：**只出报告与建议名，绝不改名**。
   如将来确实要改名，必须满足三点：独立工具（如 `file_index_rename`）、默认关闭的显式开关、每步 dry-run 预览 + 可撤销日志。

### L4 · 可选：模糊语义检索

解决"记不清词、只记得大概意思"。建议顺序：
1. 先用**本地 BM25 / 字符 n-gram**（零依赖、纯 SQL+JS），投入小、见效快；
2. 确实不够再考虑向量模型 + `sqlite-vec`（需确认 Node 内置 sqlite 的扩展加载能力）。

## 6. 验收标准（可测）

1. **案例回归**：搜「空洞骑士 鲸鱼」→ 必须命中 `卡通风格骑马.png`，且标注"仅内容命中（文件名不含鲸鱼）"。
2. **文本类抽检**：随机 20 个 md/docx/pdf，用**正文里出现、文件名里没有**的词搜 → 命中率 ≥ 90%。
3. **零破坏**：整套流程跑完后，对扫描目录抽样 200 个文件比对 mtime/大小/hash → **零变化**。
4. **幂等**：重复跑 enrich 不产生重复行、不重复调用模型（靠 `enrich` 状态 + `enrich_ver`）。
5. **断点续跑**：中途 kill 子进程后重跑，未完成的文件继续，已完成的不重做。
6. **性能**：`searchFiles` 在 1 万行规模 p95 < 300 ms（现有 LIKE 方案已有余量）。
7. **可解释**：任一结果都能回答"为什么它出现在这里"（命中列 + 片段）。

## 7. 开放问题（需你决策）

1. **PDF 正文抽取工具链**：纯 Node 无依赖解析 PDF 文本层不可靠。三选一：
   (a) 只取 PDF 元数据+书签+文件名，正文留给模型在环；
   (b) 复用本机已有 Python/pdftotext 工具链（需确认本机有什么）；
   (c) 引入轻量 npm 依赖（会改变插件"零外部原生依赖"的卖点）。
2. **图片看图配额**：一次性冲刺高价值子集（约 150–300 张），还是每天固定配额慢慢跑完全量 1231 张？
3. **是否要"建议名"输出**：只给报告，还是也要一键改名？（后者破坏只读承诺，需单独开关）
4. **视频/音频**：确认本期不做（21 GB 视频、176 个文件；抽帧还要临时文件，违背"不建缩略图"铁律）。
5. **代码文件**：1377 个代码文件是否也进内容索引？（利：搜函数名；弊：噪音大、体积 174 MB）
